Handover · BO / Devsite → JMS backend

What the SMS Service does today

A description of every flow the current service runs, written so the new JMS backend can replace it without breaking the Back Office, the Devsite, or the Android phones already in the field.

Source production code, branch main Scope ingest · notifications · device · auth · confirm · ops Full detail docs/jms-handover, 7 files

Merchants run Android phones with bank SIMs. The app reads incoming bank SMS and bank-app notifications, uploads them, and sends a heartbeat. The server parses each SMS into a statement — amount, reference code, balance, time. The BO matches statements against claimed deposits and credits the player.

Three things carry money: SMS ingest, ping, and the confirm loop. Everything else is operational tooling. This page summarises all of it; the markdown set carries field-level contracts, error codes and file references.

01Where things live

Two databases, no shared tables. Raw SMS, parsed statements, devices, users and regex templates exist only inside the SMS Service. The BO keeps deposits, accounts and the link tables. Retiring the service makes the new backend the system of record for that data.

02The five questions, answered

Q1What happens to an SMS sent to the server?

Nine steps, and the response is returned before parsing runs — the app never learns whether its SMS produced a statement.

flowchart TD
  A["POST /api/Sms/add"] --> B{"payload valid?"}
  B -- no --> E1["400 · 1006"]
  B -- yes --> C{"phone valid?"}
  C -- no --> E2["400 · 1007"]
  C -- yes --> D{"sender allowed?"}
  D -- no --> S1["200 · 0000 and dropped"]
  D -- yes --> F{"device logged in?"}
  F -- no --> E3["400 · 1001"]
  F -- yes --> G{"signature valid?"}
  G -- no --> E4["400 · 1002"]
  G -- yes --> H["store raw SMS, unique index"]
  H --> I["200 · 0000"]
  H --> J["async parse"]
  J --> K{"parsed?"}
  K -- yes --> L["store statement, balance check, alert"]
  K -- no --> M["forward to BO OTP hook, alert"]

Filter — sender allow-list of 13 fixed senders plus a sender-mask table, cached 30 s, enabled in both productions. Verify — SHA256(phone + deviceId + deviceSecret), with phone and device id taken raw from the request JSON: static per device, no timestamp or nonce. Store — raw row deduplicated on (sender, SHA256 body, phone, receivedTime); statement deduplicated on (bank, refCode, phone, transferredTime). Parse — four hard-coded parsers in order bKash, Nagad, Rocket, Upay (15 message shapes between them), then database regex templates by sender mask, ordered by priority.

  • 0000 success · dropped · duplicate
  • 1001 device
  • 1002 signature
  • 1004 internal
  • 1006 payload
  • 1007 phone
Carries money

A rejected sender and a duplicate both return success, so the app cannot tell "stored" from "ignored". Changing that changes the Android app too.

The parse queue is in memory: a restart loses queued work, leaving a raw SMS that never becomes a statement. The new backend needs a durable queue or an outbox.

Q2The same question, for notifications

"Noti" is two unrelated things. Only one of them touches the SMS Service.

DirectionBO → devicedevice → server
Handled bySMS ServiceBO directly, the service is not involved

Outbound push: send, edit, resend, plus reads for statistics and recipients. Recipients resolve from master merchant code plus a phone list; a phone with no device is still recorded, so operators see who was unreachable. Delivery is by FCM token, 500 per batch, five batches in flight. A fire-and-forget callback reports counters back to the BO — with no retry today.

Bank-notification ingest runs on the BO and is the better-built of the two pipelines. Worth copying, because the BO team will ask for the same visibility over SMS:

  • the signature covers title and body, and is verified on the raw request before normalisation;
  • deduplication uses a canonical event id: SHA-256 over length-prefixed fields after NFKC normalisation and whitespace collapsing;
  • the request is parked in an inbox and acknowledged immediately; a scheduler drains it, claiming batches atomically and reclaiming rows stuck over five minutes;
  • retry is exponential with a cap, ten attempts, and exhausted rows are kept with their last error rather than deleted;
  • matching requires an exact amount inside a time window, and two candidates means nothing is confirmed — an operator decides.

Q3Does ping do anything besides recording device status?

Yes — five things, and one of them is the most load-bearing call in the system.

#Side effectWhy it matters
1Version gaterejects outdated apps with code 1008 before anything else. The gate lives on the ping path, not on the version endpoint
2Device row updatelast ping, UI version, and the FCM token — push keeps working because token refresh rides the heartbeat
3Heartbeat forwarded to the BOan account with no recent ping is excluded from deposit routing. A ping outage stops the business, and has done so before
4Client IP captureclassified direct / CDN / proxy, alerted for two tenants — operators spot phones that moved
5Leader token cleanupsigning a device out clears leader push tokens on the same device

Ping carries no configuration and no commands back to the app: no force logout, no force update, no reset. The app learns those by calling the version endpoint. The gate itself is narrow and must be reproduced exactly: only UI version 2 is gated, and an app reporting version 0 is never blocked.

Q4What to watch out for when activating a SIM

Activation returns the device secret encrypted with a public key the app supplies; the plaintext never crosses the wire.

flowchart LR
  NEW["no row for this SIM"] -->|activate| ACT["active · secret issued"]
  ACT -->|"activate, same device"| SAME["same secret returned
login state untouched"]
  ACT -->|"activate, other device"| ERR["rejected · 2002"]
  ACT -->|"sign out or reset"| OUT["device id and secret cleared"]
  OUT -->|activate| NEWSEC["new secret issued"]
  • One SIM binds to one device. Moving a SIM needs a reset first, otherwise activation fails with 2002.
  • Re-activating the same device returns the existing secret and does not touch login state — the app relies on this to survive a reinstall.
  • Activation verifies the account against the BO when enabled. Every failure mode — rejection, timeout, malformed response — currently collapses into one code, so an operator cannot tell "not registered" from "BO is down". Separate them.
Port hazard

The secret itself is opaque — it embeds a fresh GUID, is never re-derived, and is only read back from the device row, so migrating it is a column copy.

The hazard is the signed string: it is phone plus device id exactly as they appear in the request JSON, untrimmed and un-normalised, while the device row is found by the normalised phone. A backend that normalises before signing breaks the entire fleet at once — verify against real rows before cutover.

03The money path

Matching stays on the BO. The new backend stores statements and confirmation records, and the BO pulls candidates by reference code.

sequenceDiagram
  participant U as End user
  participant BO as BO
  participant JMS as JMS backend
  U->>BO: claim deposit, gets a reference code
  loop scheduler tick
    BO->>JMS: POST /statements/by-refcodes
    JMS-->>BO: matching statements
    BO->>BO: apply matching rules
    alt exactly one match
      BO->>BO: credit deposit, link statement
      BO->>JMS: POST /statements/mark-confirmed
      JMS-->>BO: ok, or conflict if already used
    else no match
      BO->>BO: retry next tick until the claim times out
    end
  end

Two endpoints, not one

by-refcodes lets the BO read. mark-confirmed lets the BO say which statement was consumed by which deposit. The second exists so a statement can never be spent twice: the BO has its own link table, but a guard held by the owner of the data is what makes double-crediting impossible under retry, and what lets support answer "was this SMS already used, and for what?".

Required semantics: idempotent for the same pair; a distinguishable conflict when the same statement arrives with a different deposit — never a silent overwrite.

The matching rules, so both sides agree

  1. reference code on the deposit equals the reference code on the statement;
  2. amounts are exactly equal;
  3. statement transfer time minus six hours is earlier than the claim time;
  4. the statement's bank is the paired bank of the account, and the phone matches — this one applies on the target path only, not on the live one;
  5. a matched statement leaves the candidate set — one deposit consumes one statement.

Rule 4 is a new restriction that takes effect when the pull-by-reference-code path goes live: a statement the current path accepts can be rejected by the new one. Both paths get reconciled against the same data before the switch.

Read twice

Transfer time is parsed out of the SMS body and is bank local time, UTC+6 — not UTC. Rule 3 exists because of it. Changing the meaning of that field without renaming it makes deposits stop matching silently, which is the worst failure available here. Return an unambiguous UTC value alongside the original local one and let the BO migrate.

Identity and replay

The BO deduplicates on the statement id and keeps it as a foreign key. One source SMS must keep one id for its lifetime, including after a re-parse — or the response must carry the previous id as well, or old statements arrive at the BO looking new.

04The integration surface

Four different signature schemes coexist today, and a large share of the traffic carries none at all, relying on network placement. The new backend should expose one scheme for service-to-service traffic: HMAC over method, path, body digest, timestamp and nonce, bounded window, per-environment keys, separate keys for read and write.
